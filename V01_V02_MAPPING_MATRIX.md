# Calico v01 to v02 Mapping Matrix

## Purpose

This is Step 3 of the v02 build manual. It compares the documented v01
implementation with the approved v02 static shell at tag
`v02-static-shell-baseline` plus the currently approved shell refinements.
It is a planning and parity record only: **no v02 UI, design, or behaviour was
changed to create this document.**

### Reading the Matrix

- **Designed surface, not linked:** the approved v02 visual counterpart exists,
  but it is currently fixture-driven/static and needs the v01 mechanism linked
  in Step 5.
- **Required now:** required for v02 feature parity once the associated logical
  slice is ported.
- **Designed but deferred:** the visual surface exists, but connecting its v01
  mechanism belongs to a later slice (for example hosting/auth).
- **v01-only spillover:** the v01 column is intentionally populated while the
  v02 column is blank. No approved current v02 counterpart exists, so Step 4
  must design one before the mechanism can be ported, or the user must make an
  explicit retire/defer decision.
- **v02-only spillover:** the v02 column is intentionally populated while the
  v01 column is blank. It is a new approved visual concept; it needs a product
  decision/data shape before implementation.
- **Data compatibility:** “direct reuse” means the v01 stored shape can remain
  the source shape inside a v02 state module. “Migration required” means v02
  needs a deliberate conversion/adapter. “No existing data” means the v02
  visual concept has no v01-backed persisted field.

## Explicit v01 Spillover Requiring a Future v02 Surface or Decision

The rows intentionally blank in the v02 column are the current answer to
“what is left over?” They are not omissions. Before any one is ported, Step 4
must produce its exact v02 design or the user must explicitly retire it:

1. Daily intensity controls (and, separately, the retired baseline nudge).
2. Weekday-capacity settings.
3. Task priority control and its mandatory/optional conflict policy.
4. Detailed task recurrence: custom weekdays, intervals, start/end rules.
5. Detailed event recurrence: custom weekdays, intervals, start/end rules.
6. Drag/drop schedule manipulation and a keyboard-accessible equivalent.
7. Daily check-in prompt, currently intentionally retired/deferred.
8. Conflict overwork, demote-other-tasks, and intensity-redistribution choices.
9. A normal Settings entry point for Sign out.
10. Mobile UI and the full empty-state experience, both deliberately deferred.

## Explicit v02 Spillover Requiring a Product/Data Decision

The rows intentionally blank in the v01 column are approved visual concepts
that have no exact v01 data/mechanism. They must be specified before their
buttons are connected:

1. Explicit Incomplete outcome distinct from partial, skipped, or neutral.
2. Conflict choice “Split the work.”
3. Conflict choice “Choose another time.”
4. Project archive rather than delete/unassign.
5. A Review both plans sync-merge flow.
6. Resolved-review history.
7. Import comparison counts (derived, not persisted).

## Immediate Conclusion

The core v01 planning engine, state, tasks, events/availability, working
hours, projects, search, backup/reset, task time controls, completion, Review,
and email-sync safety all have either a direct or a partial approved v02
counterpart. The visual shell is ready for those porting slices once the
matrix-specific interaction specifications are written.

The unmatched items above must remain visibly unmatched until a design or
product decision exists. Nothing in this matrix authorises adding them to the
approved v02 shell.
